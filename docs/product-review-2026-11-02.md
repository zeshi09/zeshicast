# Продуктовое ревью: zeshicast против Raycast 2.0 и Vicinae (2026-11-02)

Продолжение `docs/vicinae-comparison-2026-09-19.md` и `docs/full-review-2026-10-04.md`.
Исполнительный план по итогам — `docs/product-plan-2026-11-02.md`.

**Данные:** `zeshicast` HEAD `2809873` (07.10.2026) + незакоммиченная правка
`src/action.rs`; `vicinae` `v0.29.2`, последний коммит 28.10.2026 (локальная копия
`~/Git/vicinae`); Raycast 2.0 — по публичному changelog (закрытый код).
**Метод:** чтение кода, прогон `cargo test` (без фич), `cargo fmt --check`,
воспроизведение поиска через CLI на реальном `$HOME`, `git log` обоих проектов,
сверка с планом 2026-09-19.

## Резюме

1. **Инженерно zeshicast сильнее Vicinae, как продукт — слабее и Vicinae, и
   Raycast 2.0.** Оценка (субъективная, из 10): zeshicast — инженерия 8 /
   продукт 4; Vicinae — 5–6 / 8; Raycast 2.0 — продукт 9.5 (на Linux его нет).
2. **Стратегия A+B из сравнения 19.09 верная, исполнение — нет.** За 6 недель:
   12 коммитов, все — укрепление по ревью 04.10 и UI-полировка. Фазы 0–2 плана
   2026-09-19 (замеры, `--toggle`, `--dmenu`, вставка, deep links, онбординг,
   поиск в настройках, ru-локаль) — **0 из 9 шагов**, хотя каждый оценён в S.
3. **Vicinae за то же время** выпустил 75 коммитов (v0.29.0 → v0.29.2),
   опубликовал браузерное расширение (закладки, история, релиз-воркфлоу) — то
   «окно возможности», которое мы отмечали в сентябре, закрыто. Bus factor у них
   улучшился: в топе 4–5 авторов с сопоставимым вкладом.
4. **Raycast 2.0** вышел из беты 25.08.2026 (macOS + Windows, Linux нет). Это
   задаёт планку UX: файлы прямо в root search через собственный индексер на
   Rust, хоткеи и алиасы из root search, буфер с сохранением исходного формата,
   AI (Agents/Skills/Memory, MCP-реестр), диктовка.
5. **Найден реальный баг ядра поиска:** `~/Downloads` фактически не
   индексируется (раздел 2.1). Это ровно та функция, которую пользователь
   пробует в первую минуту.
6. **Рекомендация:** развернуть порядок работ — сначала ежедневный вход/выход и
   качество поиска (2–3 недели), затем измеримость, затем SDK расширений как
   публичный актив. Новые волны ревью/UI-переработок — на паузу.

## 2. Ревью кода

### 2.0 Базовая линия

| Проверка | Результат |
| --- | --- |
| `cargo test` (без фич) | ✅ 278 passed (274 lib + 4 CLI) |
| Всего `#[test]` | 349 |
| `cargo fmt --check` | ❌ падает: незакоммиченная перестановка импортов в `src/action.rs:1001` |
| `unwrap()/expect()` вне тестов | 1 (`src/search/scripts.rs:262`, защищён проверкой выше) |
| `unsafe` | только FFI к gtk-layer-shell и `g_unix_signal_add_full`, с `SAFETY`-комментариями |

### 2.1 🔴 Файловый индекс пропускает приоритетные каталоги (CONFIRMED)

`src/search/files.rs:93-117` (`load_file_index`). Корни обхода в порядке:
`cwd.parent()`, `cwd`, затем `Code/Documents/Downloads/Desktop/Projects`, затем
`$HOME`. У демона (systemd user unit, спавн из niri) `cwd = $HOME`, значит
**первым** обходится `/home`. Обход в глубину (до глубины 5) упирается в
`MAX_INDEXED_FILES = 10_000` где-то в `~/Git`/`~/Code`; до приоритетных корней
дело не доходит, а повторно они не обходятся, потому что их дети уже в `seen`.

Воспроизведение (из `$HOME`, файлы существуют):

```text
$ zeshicast file "ошибок Go"        → 1. File  100 ошибок Go.pdf - ~/Documents   (повезло с порядком)
$ zeshicast file dogovor_postavki   → No results.                                (файл в ~/Downloads)
$ zeshicast file dpa_personal       → только Clipboard-строки                     (файл в ~/Downloads)
```

Отдельная проблема той же функции: если процесс запущен из `/`, первым корнем
становится сама файловая система.

**Фикс:** приоритетные корни первыми, `cwd`/`cwd.parent()` убрать; квоту на
корень (чтобы один большой каталог не съедал весь лимит); тест на переполненном
временном `$HOME`. Шаг Q0.1 плана.

### 2.2 🟠 Явный префикс `file …` не изолирует провайдеры

`src/search/mod.rs:207` включает файловый поиск по `file `/`find `, но
`ClipboardProvider` (`src/search/snapshot.rs:156`) продолжает отвечать на тот же
запрос — в выдаче `file dpa_personal` только строки буфера. Префикс должен
означать «только файлы», как `system`/`niri`/`hypr`. Шаг Q0.3.

### 2.3 🟠 Нечёткий поиск слабее конкурентов

`src/search/mod.rs:266` (`fuzzy_score_lower`):

- нет бонуса за начало слова / аббревиатуру: `vsc` не выделяет
  «Visual Studio Code», `ff` — «Firefox»;
- `text_lower.len()` и `find()` — **байты**, а не символы: кириллические
  названия получают удвоенный штраф по длине и позиции (для пользователя с
  русскими именами файлов это заметно);
- нет учёта раскладки (`ашкуащч` → `firefox`) — у Raycast и Vicinae тоже нет,
  но для ru-пользователя это дешёвое преимущество.

Шаг Q1.1.

### 2.4 🟠 Обещание «<50 мс» не измерено

`PRODUCT.md` обещает sub-50 ms, но метрик нет (P0.1 плана 19.09 не начат). При
этом `src/bin/zeshicast-gtk.rs:122` по умолчанию выставляет
`GSK_RENDERER=cairo` (программная отрисовка) из-за обрезки глифов на части
драйверов. На HiDPI с анимациями это работает против цели. Решение должно
приниматься по цифрам. Шаги Q2.1–Q2.2.

### 2.5 🟡 Повторяющийся дрейф форматирования

Ревью 04.10 фиксировало незакоммиченную перестановку импортов в
`src/search/scripts.rs`; сейчас то же самое в `src/action.rs`. Похоже, внешний
инструмент (редактор/агент) вызывает `rustfmt` без `edition = 2024` и сортирует
по правилам старого style edition. Нет `rustfmt.toml`, нет pre-commit. Шаг Q0.2.

### 2.6 🟡 Ручной FFI к gtk-layer-shell

`src/bin/zeshicast-gtk.rs:18-40` и `src/ui/osd.rs:609-653` — два независимых
`extern "C"` блока с константами из C-заголовков. Работает, но хрупко при
обновлении библиотеки и дублируется. Шаг Q0.4 (низкий приоритет).

### 2.7 Сильные стороны (подтверждены кодом)

- Единственная точка исполнения `execute()` + `ExecutionTicket`; права
  расширения ограничены манифестом (`declared ∩ manifest`); ответ расширения
  проходит тот же gate и не может эскалировать.
- Риск-классы действий с подтверждениями (Shell/Destructive/Power/Kill).
- 349 тестов в трёх конфигурациях CI, `cargo-deny`, SHA-пины экшенов,
  docs-as-code (`documented_invariants_have_the_tests_they_name`).
- Дисциплина паник реальная, а не декларативная.
- Ядро (`search/`, `app/`, `services/`, `action.rs`) почти не зависит от GTK —
  это упрощает тестирование и любые будущие смены UI (см.
  `docs/amane-migration-analysis-2026-10-11.md`).

## 4. Где мы выигрываем и как это продавать

1. **«Лаунчер, которому можно доверить расширения».** Модель прав — уникальна в
   сегменте, но невидима: нет SDK, нет линтера, нет экрана «что запрашивает это
   расширение».
2. **«Один процесс вместо swaync + playerctl + nm-applet + pavucontrol +
   cliphist + btop».** Командный центр — реальное отличие, но открывается только
   тем, кто уже прошёл через хоткей, поиск и вставку.
3. **Ноль телеметрии, локальные данные, Nix-first.** Аудитория NixOS/niri ценит
   это прямо.

## 6. Рекомендация

- Порядок: **Q0 (баги, гигиена) → Q1 (ежедневный вход/выход) → Q2 (замеры) →
  Q3 (первый запуск) ∥ Q4 (релизы) → Q5 (SDK) → Q6–Q8**.
- Метрика успеха квартала — не число тестов, а «новый пользователь NixOS/niri
  за 5 минут: поставил, вызвал хоткеем, нашёл файл из Downloads, вставил
  элемент буфера, увидел командный центр».
- Не делаем: Node/React-рантайм, свой стор, X11/macOS/Windows, телеметрию
  (решения 19.09 остаются в силе).
