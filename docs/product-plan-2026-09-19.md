# План развития продукта по итогам сравнения с Vicinae (2026-09-19)

**Основание:** `docs/vicinae-comparison-2026-09-19.md` (сравнение с Vicinae v0.29.0).
**Стратегия:** A «безопасный Raycast для Linux» (публичный capability-gated SDK +
реестр в стиле git/nix) **+** B «Linux control center» (углубление половины,
которой у конкурента нет). Вариант C (Node/React-рантайм, хостинг стора) — вне
плана, см. «Не делаем».
**Принципы:** fail-closed; одна точка исполнения (`execute` + `ExecutionTicket`);
ни одного изменения поведения без теста; шаг = один коммит = один проверяемый
результат; никакой телеметрии; никаких сетевых вызовов без явного действия
пользователя; порядок фаз фиксирован, шаги внутри фазы — можно параллельно.
**Оценки:** S — дни, M — 1–2 недели, L — месяц+.
**Проверка каждого шага:** `cargo fmt --check`; clippy и тесты в трёх
конфигурациях (`--features gui,layer-shell` через `nix-shell shell.nix`,
`--features desktop`, без фич); для шагов с документацией — тест
`documented_invariants_have_the_tests_they_name`.

---

## Не делаем (зафиксировано)

| Отказ | Причина |
| --- | --- |
| Node/React-рантайм и Raycast API | 56k LOC TS у конкурента; наш актив — проверяемость, а не широта |
| Хостинг стора расширений | Реестр в git/nix даёт распространение без инфраструктуры и без доверия к серверу |
| X11, macOS, Windows | Противоречит Wayland-модели (`layer-shell`, свой буфер, композиторные действия) |
| Телеметрия | Продуктовое свойство, зафиксировано в настройках |
| Раскрытие сниппетов через udev-ввод | Синтетический ввод — отдельная модель прав; возвращаться только к P5.x при появлении запроса |
| Скриншоты/трей как первый приоритет | Дают мало по сравнению с ценой; см. P5.2 (гейт) |

## Фаза 6. DoD (приёмка всего плана)

- `cargo fmt --check` чисто; clippy без замечаний в трёх конфигурациях; тесты зелёные
  (`gui,layer-shell` / `desktop` / без фич).
- Каждый шаг: коммит с тестом, названным в теле коммита; для шагов с
  документацией — `<!-- test: ... -->` в `docs/security.md`/`README.md` и
  проходящий `documented_invariants_have_the_tests_they_name`.
- Метрики из P0.1 перемерены и вписаны (до/после) в `docs/development.md`.
- Обновлены `docs/README.md` (индекс), `README.md` (возможности), `docs/security.md`
  (новые инварианты: версия протокола, реестр, журнал прав, шифрование).
- Итоговый документ приёмки `docs/product-acceptance-2026-XX-XX.md`: шаг → коммит →
  тест → что осталось за человеком (как в `docs/remediation-acceptance.md`).

## Риски и как их снимаем

| Риск | Снятие |
| --- | --- |
| Вставка в окно (`wtype`) ведёт себя по-разному в композиторах | Действие через gate с подтверждением; при недоступности `wtype` — честное «недоступно», без фолбэка в `sh -c` |
| Линтер манифеста со временем расходится с парсером | Один парсер: линтер вызывает `parse_extension_manifest`, а не свою копию |
| Шифрование БД ломает существующие данные | Миграция схемы отдельным шагом, тест на реальной БД предыдущей версии, ключ рядом с БД 0600 |
| Реестр расширений становится каналом доставки кода | Хеш обязателен; установка только с подтверждением; declared capabilities не расширяются установкой |
| Watcher индекса жжёт CPU на большом `$HOME` | Debounce, лимиты, пауза при скрытой палитре (механизм уже есть в `poll_cache`) |

## Решения владельца (с дефолтами, чтобы не блокировать план)

1. **Реестр расширений:** дефолт — индекс в git + nix-хелпер; хостинг не делаем.
2. **i18n:** дефолт — каркас + `ru` в фазе 2, остальные языки — сообщество.
3. **Wayland-only:** дефолт — да.
4. **Трей:** дефолт — P5.2 остаётся гейтом, не начинаем без решения.
5. **Живые вкладки браузера:** дефолт — P5.3 гейт; при старте — сначала проверить,
   не появилось ли расширение у конкурента в сторах (окно возможности).
6. **JSON-RPC как публичный контракт:** дефолт — да, с версией протокола и
   политикой: новая версия добавляет поля, не ломая старые; удаление — только
   через смену версии.

## Порядок и почему

1. **Фаза 0** — без базовых чисел нельзя утверждать, что мы «быстрее»; без
   Non-goals план расползается.
2. **Фаза 1** — самые дешёвые разрывы в ежедневном UX; после неё продукт
   перестаёт требовать правки конфигов от пользователя.
3. **Фаза 2** — то, что отделяет «инструмент» от «продукта» для человека, который
   не читает README (поиск в настройках, первый запуск, язык).
4. **Фаза 3** — сделать видимым наш главный актив: расширения с потолком прав и
   журналом. Это единственная ось, где мы уже сильнее конкурента.
5. **Фаза 4** — приватность данных на диске (у конкурента шифрование есть, у нас
   нет) и скорость файлового поиска.
6. **Фаза 5** — углубление командного центра; два последних пункта — только по
   решению владельца.
